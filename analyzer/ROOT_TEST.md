# Root-тест первого этапа

## Назначение

Сценарий проверяет на целевой двухсокетной машине:

1. CPU/RAPL recorder от обычного пользователя и от root.
2. Новую запись CPU-счетчиков через ограниченный PCM backend от root.
3. Чтение PCM-интерфейсом MSR регистров энергии package и DRAM на каждом сокете.
4. Доступ к core PMU через Linux `perf_event_open` для cycles и instructions.
5. Состояние `nmi_watchdog`, `perf_event_paranoid` и параметра MSR
   `allow_writes` до и после теста.

Для запуска не требуется менять права на устройства, capabilities,
`perf_event_paranoid`, watchdog или профиль TuneD. Модуль `msr` должен быть
загружен; если доступ или модуль отсутствует, тест сообщит об ошибке и
сохранит диагностику. Он не загружает модуль самостоятельно.

## Что происходит с оборудованием

`pcm-msr-check` использует локальную модифицированную библиотеку PCM и
открывает MSR с `O_RDONLY`. Он читает регистры `0x606`, `0x611` и `0x619`
по одному доступному CPU каждого сокета и делает два снимка с интервалом
около одной секунды. Одновременно снимаются соответствующие значения Linux
powercap. Инструмент не вызывает `PCM::getInstance()`, `PCM::program()` и
`PCM::cleanup()`, не программирует PMU и не изменяет `allow_writes`, RDT или
uncore.

`pmu-perf-check` отдельно открывает через ядро два системных perf-события для
первого online CPU. Пока файловые дескрипторы открыты, ядро размещает эти
события на core PMU; при завершении дескрипторы закрываются. Счетчики других
процессов явно не сбрасываются. Возможны конкуренция за PMU, мультиплексирование
и небольшая нагрузка на систему. Учитываются `enabled_ns` и `running_ns`,
но значения не масштабируются и не служат тестом точности.

PCM backend recorder вызывает `PCM::getInstance()`, `PCM::program()` и
`PCM::cleanup()` в локальном режиме analyzer core-only. Он использует
read-only MSR и core perf-группы, не выполняет RDT/uncore-инициализацию,
не меняет watchdog и параметр `allow_writes`, и не переходит к прямому
программированию MSR. Ядро размещает perf-события на PMU на время записи;
возможны конкуренция и мультиплексирование. Сценарий проверяет PCM-записи
для представительного CPU каждого сокета и доступные дельты. Один короткий
запуск на целевой машине завершился успешно; проверка под нагрузкой остается.

PCM и powercap могут использовать один аппаратный источник энергии, а их
чтения последовательны. Они не являются независимыми физическими измерениями.
Сценарий проверяет только ограниченный режим PCM core-only. Он **не проверяет
стандартную полную инициализацию PCM, uncore PMU**, память, UPI или IIO.
Для них потребуется отдельный тест владения и совместимости счетчиков.

Закройте другие активные инструменты мониторинга PMU, если хотите исключить
конкуренцию. Остановите эксперимент, если система ведет себя неожиданно. Не
используйте `kill -9`: штатное завершение дает инструментам возможность
освободить ресурсы. Проверка трех настроек до/после не доказывает неизменность
всех остальных состояний системы.

## Сборка

Выполните из корня проекта обычным пользователем:

```sh
cmake -S analyzer/third_party/pcm -B analyzer/build/pcm \
  -DPCM_BUILD_EXECUTABLES=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build analyzer/build/pcm --target PCM_STATIC_SILENT --parallel 2
cmake -S analyzer -B analyzer/build -DCMAKE_BUILD_TYPE=Debug \
  -DANALYZER_PCM_LIBRARY="$PWD/analyzer/build/pcm/src/libPCM_STATIC_SILENT.a"
cmake --build analyzer/build --parallel 2
ctest --test-dir analyzer/build --output-on-failure
```

Нужны CMake, C++17, `libsystemd` с `sd-json`, pkg-config, `sudo`, `jq`, `awk`,
`cmp` и `lscpu`. Используйте библиотеку, собранную из локальных исходников:
скопированный исходный prebuilt-архив не содержит read-only расширения.

## Запуск

Запустите в своем терминале из корня проекта:

```sh
bash analyzer/tests/root-test.sh
```

Сценарий напечатает каталог доказательств, созданный через `mktemp` в
`${TMPDIR:-/tmp}`, затем вызовет `sudo -v`. Пароль при запросе вводится вами
непосредственно в терминале. Последующие команды используют `sudo -n`, без
повторного интерактивного запроса. При отказе аутентификации тест останавливается
до аппаратной диагностики.

Последовательно выполняются две трехсекундные записи CPU/RAPL, одна
трехсекундная запись PCM и две примерно односекундные аппаратные проверки.
Сценарий не удаляет результаты и не
перезаписывает существующие каталоги. Root-запись принадлежит root; остальные
файлы доступны запустившему пользователю. Каталог имеет ограниченные права.

## Результат

`RESULT: PASS` означает, что все три записи завершились успешно, PCM recorder
сохранил оба CPU-счетчика на представительном CPU каждого сокета и получил
доступные дельты, для двух сокетов
получены и изменились значения MSR энергии package/DRAM, прочитаны powercap,
два perf-счетчика продвинулись и три проверенные настройки совпали до/после.
Это проверка доступности и базовой работоспособности, не сертификация точности,
накладных расходов или полного PCM.

### Прерывание и повторный запуск

После успешного сценария проверьте завершение и освобождение счетчиков. В
своем терминале выполните команды ниже; после нескольких секунд записи нажмите
`Ctrl+C`. Код выхода 130 при таком прерывании ожидаем.

```sh
PCM_TEST=$(mktemp -d "${TMPDIR:-/tmp}/analyzer-pcm-interrupt.XXXXXXXX")
sudo analyzer/build/analyzer record --config analyzer/examples/pcm-interrupt.json --output "$PCM_TEST/interrupted"
sudo cat "$PCM_TEST/interrupted/manifest.json" | jq '{status,pcm_status,pcm_error,sample_count}'
sudo analyzer/build/analyzer record --config analyzer/examples/pcm.json --output "$PCM_TEST/repeated"
sudo cat "$PCM_TEST/repeated/manifest.json" | jq '{status,pcm_status,pcm_error,sample_count}'
printf 'Evidence directory: %s\n' "$PCM_TEST"
```

Ожидается `interrupted` у первого запуска и `complete`, `pcm_status=available`
у второго. Первый запуск должен содержать как минимум два снимка для проверки
дельт; не нажимайте `Ctrl+C` сразу после старта. Не запускайте повторно в те же
каталоги, поскольку recorder не перезаписывает существующие данные.

При `RESULT: FAILED` посмотрите `*.err`, `*.tsv`, `*.before` и `*.after`
в напечатанном каталоге. В частности:

- Ошибка PCM может указывать на отсутствие доступа к MSR или неподдерживаемый
  регистр. Сценарий не меняет права для исправления ошибки.
- Ошибка perf может означать недостаточные права, недоступное событие или
  занятые ресурсы. Нулевое время `running_ns` не считается успешным тестом.
- Различие файлов настроек требует отдельного выяснения причины; сценарий не
  пытается автоматически восстанавливать системные параметры.

Для дальнейшего анализа сообщите путь каталога, итоговый вывод и содержимое
файлов ошибок. Логи содержат технические сведения о системе; перед передачей
за пределы машины их следует просмотреть.

## Выполненный запуск

26 ноября 2026 года оператор выполнил предыдущую версию сценария на целевой системе с двумя
Xeon Gold 6248 и ядром Linux `7.3.4-300.fc45.x86_64`: итог `PASS`. Обе записи
recorder завершились со статусом `complete`, в каждой получено четыре снимка;
журналы ошибок пусты. На обоих сокетах прочитаны и изменились MSR-счетчики
энергии package и DRAM; два perf-события выполнялись без мультиплексирования
в течение данного интервала. `nmi_watchdog=0`, `perf_event_paranoid=2` и
`allow_writes=on` совпали до и после теста. Значение `allow_writes=on` было
установлено до запуска теста и не является требованием analyzer.

Локальные результаты находятся в `/tmp/platform-analyzer-root-test.FLyd7d0Z`;
временный каталог может быть удален системой и не является частью Git.
Этот результат относится только к границам проверки, указанным выше; он не
подтверждает полную инициализацию PCM, независимую точность энергии или
поведение под нагрузкой. Добавленный позднее PCM backend этим запуском не
проверялся.

В тот же день оператор выполнил расширенный сценарий: итог `PASS`. PCM recorder
завершился со статусом `complete`, записал по четыре снимка для 40 логических
CPU и получил 240 доступных дельт инструкций и тактов. Ошибок в журнале нет;
имеются информационные сообщения PCM. Проверенные параметры `nmi_watchdog=0`,
`perf_event_paranoid=2` и `allow_writes=on` не изменились. Локальные результаты
находятся в `/tmp/platform-analyzer-root-test.5TYLyHtp`; временный каталог
может быть удален системой и не является частью Git. Отдельная проверка
прерывания и повторного запуска с реальным PCM пока не подтверждена.
